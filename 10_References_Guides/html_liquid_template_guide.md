# HTML And Liquid Template Guide

Use this guide when reading or editing `_includes/*.html`, `_layouts/*.html`, or small raw-HTML blocks inside Markdown pages. The site is not just plain HTML: Jekyll reads Markdown, YAML data, Liquid template syntax, SCSS, and JavaScript, then combines them into the final pages in `_site/`.

## The Basic HTML Shape

Most HTML elements follow this pattern:

```html
<tagname attribute="value">The content goes here</tagname>
```

The parts are:

| Part | Meaning |
| --- | --- |
| `<tagname ...>` | The opening tag. It starts the element. |
| `attribute="value"` | Extra information on the element. Attributes usually configure links, classes, accessibility labels, or scripts. |
| `The content goes here` | Text or nested HTML inside the element. |
| `</tagname>` | The closing tag. It ends the element. |

Example from the breadcrumb include:

{% raw %}
```html
<a href="{{ '/' | relative_url }}">Home</a>
```
{% endraw %}

This creates a link. The `href` attribute is the target URL. The text between the tags is what the reader sees.

Some elements are usually empty in this site because JavaScript fills them later:

```html
<nav id="page-toc-list" class="page-toc__list"></nav>
```

That `nav` starts empty, then `assets/js/page-toc.js` adds links after the page loads.

## Comments In HTML And Liquid Files

Use Liquid comments for author-facing notes in templates:

{% raw %}
```liquid
{% comment %}
This explains the template source but will not appear in the published HTML.
{% endcomment %}
```
{% endraw %}

Use normal JavaScript comments inside `<script>` blocks:

```js
// This explains JavaScript behaviour.
```

Avoid ordinary HTML comments for long template notes:

```html
<!-- This appears in the generated page source. -->
```

HTML comments are valid, but they are shipped to the browser. Liquid comments are better for internal documentation.

The remote Cayman theme also supplies the outer `html`, `head`, `body`, page header, and content shell. This repository normally edits the inner page content through `_layouts/custom.html` rather than writing the whole document frame by hand.

You do not usually write `mjx-container` yourself. MathJax creates it in the browser after it reads page equations. The site styles it because it is the wrapper around rendered equations:

```scss
.main-content mjx-container {
    overflow-x: auto;
}
```

This reads  "inside the main content area, if MathJax creates an equation container, let it scroll sideways when the equation is too wide."

## Attributes Used So Far

| Attribute | Built in or custom? | Meaning in this site |
| --- | --- | --- |
| `aria-label` | Built-in accessibility attribute | Gives screen readers a clear name for navigation regions such as breadcrumbs and footer links. |
| `async` | Built-in script attribute | Lets the external MathJax script load asynchronously. |
| `class` | Built-in HTML attribute | Connects an element to SCSS styling or JavaScript behaviour. |
| `data-min-headings` | Custom data attribute | Passes the minimum heading count from Liquid to `page-toc.js`. Browser custom data attributes start with `data-`. |
| `href` | Built-in link attribute | Sets the destination for `<a>` links. |
| `id` | Built-in HTML attribute | Gives one unique target name, such as `page-toc-list` or `MathJax-script`. |
| `markdown="1"` | Kramdown/Jekyll extension, not browser behaviour | Tells the Markdown converter to process Markdown inside a raw HTML wrapper such as `<div>`. |
| `role` | Built-in accessibility attribute | Clarifies landmarks, such as `role="contentinfo"` on the footer. |
| `src` | Built-in script/image attribute | Points a `<script>` tag at a JavaScript file or CDN URL. |
| `type` | Built-in attribute | `type="module"` tells the browser that the inline script uses JavaScript module syntax such as `import`. |

## Special `markdown="1"` 

Only appeared in `markdown="1"` in `00_project_overview/knowledge_map.md`:

```html
<div class="knowledge-map-frame" markdown="1">
```
It starts a normal HTML `div`, give it the styling hook `knowledge-map-frame`, and tell Kramdown that the content inside this wrapper should still be read as Markdown."

> Kramdown is the Markdown engine used by Jekyll. Normally, when Kramdown sees a block of raw HTML, it is cautious and may leave the inside alone instead of converting Markdown syntax inside it. The attribute `markdown="1"` means "please process Markdown inside this HTML wrapper too."

Use it when you need both:

- A real HTML wrapper, usually to add a class for SCSS.
- Markdown inside that wrapper, such as headings, lists, links, code fences, or Mermaid fences.

For example:

````md
<div class="knowledge-map-frame" markdown="1">

```mermaid
graph TD
    A --> B
```

</div>
````

This will wrap the Mermaid Markdown code fence in a styled HTML box, but still let Jekyll recognise the fenced code block as Markdown. (for displaying certian code blocks)

Without `markdown="1"`, the triple backticks may be treated as plain text inside the raw HTML wrapper instead of becoming a proper code block. That would stop the Mermaid conversion chain from working cleanly.

Do not add `markdown="1"` to every HTML tag. Use it only when the content inside a raw HTML element still needs Markdown processing.

## More on Site Classes And Display Effects

They are names attached to elements:

```html
<nav class="page-breadcrumb" aria-label="Page navigation">
```

The matching SCSS selector starts with a dot:

```scss
.page-breadcrumb {
    display: flex;
}
```

Current site classes and hooks:

| Class or hook | Created by | Special display or behaviour? |
| --- | --- | --- |
| `.main-content` | Cayman theme layout | Yes. Local SCSS widens the content column and adjusts headings, images, code, tables, lists, and MathJax. |
| `.page-breadcrumb` | `_includes/page-nav.html` | Yes. Flex breadcrumb row with spacing and link styles. |
| `.page-breadcrumb__separator` | `_includes/page-nav.html` | Yes. Muted slash between breadcrumb levels. |
| `.page-toc` | `_includes/table-of-contents.html` | Yes. Hidden by default; visible only when JS adds `.is-ready`. |
| `.page-toc.is-ready` | `assets/js/page-toc.js` | Yes. Shows and styles the TOC box; sticky side rail on wide screens. |
| `.page-toc__inner` | `_includes/table-of-contents.html` | No direct SCSS rule so far; useful as a future hook. |
| `.page-toc__title` | `_includes/table-of-contents.html` | Yes. Styles "On this page". |
| `.page-toc__list` | `_includes/table-of-contents.html` | Yes. Grid layout for generated TOC links. |
| `.page-toc__link` | `assets/js/page-toc.js` | Yes. Base style for generated TOC links. |

| `.prev-next__link--next` | `_includes/prev-next.html` | Yes. Aligns the next card text right on larger screens. |

## Liquid Syntax Used In This Site

Liquid runs before the browser sees the page. It lets Jekyll insert variables, loop over data, and conditionally include HTML.

| Liquid syntax | Meaning | Site example |
| --- | --- | --- |
| `{% raw %}{{ variable }}{% endraw %}` | Output a value | `{% raw %}{{ page.section_title }}{% endraw %}` prints the section title. |
| `{% raw %}{% tag %}{% endraw %}` | Run template logic | `{% raw %}{% if page.section_title %}{% endraw %}` starts a condition. |
| `{% raw %}{% include file.html %}{% endraw %}` | Insert a reusable include | The layout inserts `page-nav.html`, `table-of-contents.html`, `prev-next.html`, and `site-footer.html`. |
| `{% raw %}{% assign name = value %}{% endraw %}` | Create or replace a variable | `prev-next.html` stores `prev_title`, `prev_url`, `next_title`, and `next_url`. |
| `{% raw %}{% if condition %}...{% endif %}{% endraw %}` | Render only when a condition is true | Breadcrumb levels appear only when the page has matching title variables. |
| `{% raw %}{% unless condition %}...{% endunless %}{% endraw %}` | Render unless a condition is true | The TOC appears unless `page.toc == false`. |
| `{% raw %}{% for item in list %}...{% endfor %}{% endraw %}` | Loop over a list | Footer links loop over `site.footer_links`; previous/next loops over `site.data.reading_paths`. |
| `| relative_url` | Filter that makes a URL work under the site's base path | Used on internal links and local script paths. |
| `| default: value` | Filter that supplies a fallback value | TOC minimum headings falls back from page to site to `3`. |
| `| replace: 'index.html', ''` | Filter that rewrites text | Previous/next normalises index URLs before comparing them. |
| `| date: "%Y-%m-%d"` | Filter that formats dates | Footer formats `site.time`. |

Important Liquid objects:

| Object | What it contains |
| --- | --- |
| `page` | Variables for the current page, from front matter and `_config.yml` defaults. |
| `site` | Site-wide config, build data, and collections. |
| `site.data` | YAML files from `_data/`, such as `site.data.reading_paths`. |
| `content` | The current Markdown page after Jekyll has converted it to HTML. |

## How HTML, Liquid, SCSS, And JavaScript Connect

HTML gives the page structure. Liquid decides which structure to print. SCSS decides how matching elements look. JavaScript changes the page after it reaches the browser.

Example:

{% raw %}
```liquid
<aside class="page-toc" data-min-headings="{{ page.toc_min_headings | default: site.toc_min_headings | default: 3 }}">
  <nav id="page-toc-list" class="page-toc__list"></nav>
</aside>
```
{% endraw %}

The connections are:

| Layer | What it does |
| --- | --- |
| HTML | Creates an `aside` and an empty `nav`. |
| Liquid | Calculates the `data-min-headings` value. |
| JavaScript | Reads `data-min-headings`, scans headings, appends `<a>` links, and adds `.is-ready`. |
| SCSS | Hides `.page-toc` until `.is-ready` appears, then styles it. |

## Five Walkthrough Levels

### Level 1: Plain Markdown Becomes Built-In HTML

Source Markdown:

```md
This is **important**.
```

This reads "write a sentence where the word `important` should be emphasised."

Generated HTML:

```html
<p>This is <strong>important</strong>.</p>
```

This reads  "make one paragraph, and mark `important` as strong text inside it."

Connected files:

| Step | File or system |
| --- | --- |
| 1 | A Markdown page contains the prose. |
| 2 | Jekyll converts Markdown to HTML. |
| 3 | `assets/css/style.scss` makes `strong, b` extra bold. |

This is the easiest pattern: no custom Liquid variable and no JavaScript.

### Level 2: Raw HTML Adds A Styling Hook

Source in `00_project_overview/knowledge_map.md`:

```html
<div class="knowledge-map-frame" markdown="1">
  ...
</div>
```

This reads  "make a wrapper around this block, attach the `knowledge-map-frame` class for styling, and still process Markdown inside the wrapper."

Connected files:

| Step | File or system |
| --- | --- |
| 1 | The Markdown page writes a real HTML `div`. |
| 2 | `markdown="1"` tells Kramdown to process Markdown inside the wrapper. |
| 3 | `assets/css/style.scss` finds `.knowledge-map-frame` and makes it wide and scrollable. |

The `div` itself is generic. The class gives it site-specific meaning.

### Level 3: Breadcrumbs Use Front Matter Or Config Defaults

Simplified template:

{% raw %}
```liquid
{% if page.section_title %}
  <span class="page-breadcrumb__separator">/</span>
  <a href="{{ page.section_url | relative_url }}">{{ page.section_title }}</a>
{% endif %}
```
{% endraw %}

This reads  "if this page has a section title, print a slash separator and then print a breadcrumb link to that section."

Connected files:

| Step | File or system |
| --- | --- |
| 1 | `_config.yml` supplies defaults such as `section_title` and `section_url`. |
| 2 | A page can override those values in front matter. |
| 3 | `_layouts/custom.html` includes `_includes/page-nav.html`. |
| 4 | Liquid prints only the breadcrumb levels that exist. |
| 5 | `assets/css/style.scss` styles `.page-breadcrumb` and `.page-breadcrumb__separator`. |

This pattern is good for page metadata that should be mostly automatic.

### Level 4: Previous/Next Links Use YAML Data And Liquid Loops

Source data in `_data/reading_paths.yml`:

```yml
- title: Example Reading Path
  pages:
    - title: First Page
      url: /section/first.html
    - title: Second Page
      url: /section/second.html
```

This reads  "define a named reading path, then list the pages in the order readers should move through them."

Connected files:

| Step | File or system |
| --- | --- |
| 1 | `_data/reading_paths.yml` defines the desired reading order. |
| 2 | Jekyll exposes it as `site.data.reading_paths`. |
| 3 | `_includes/prev-next.html` loops through the pages and compares each URL with `page.url`. |
| 4 | The include prints previous and/or next `<a>` cards. |
| 5 | `assets/css/style.scss` styles `.prev-next`, `.prev-next__link`, labels, titles, and mobile alignment. |

This pattern is more advanced because one page's navigation depends on a separate data file.

### Level 5: Dynamic Rendering Uses Markdown, Liquid, JavaScript, External Libraries, And SCSS

Mermaid diagrams are the most connected example.

Source Markdown:

````md
```mermaid
graph TD
    A --> B
```
````

This reads  "create a Mermaid diagram where node `A` points to node `B`."

What happens:

| Step | File or system |
| --- | --- |
| 1 | The Markdown page contains a Mermaid fenced code block. |
| 2 | Jekyll/Kramdown converts it to HTML such as `<pre><code class="language-mermaid">...`. |
| 3 | `_layouts/custom.html` loads the Mermaid CDN module. |
| 4 | The inline layout script finds `code.language-mermaid`, creates `<div class="mermaid">`, and moves the diagram text into it. |
| 5 | Mermaid renders that text into an SVG diagram in the browser. |
| 6 | `assets/css/style.scss` gives special layout to `.knowledge-map-frame .mermaid svg` when the diagram sits inside the knowledge-map frame. |

MathJax follows the same idea: content pages write math, `assets/js/mathjax-config.js` defines shared macros, the layout loads the external MathJax script, MathJax generates `mjx-container` elements, and SCSS keeps wide equations scrollable.

## Quick Editing Checklist

- Use normal Markdown for ordinary prose, headings, lists, tables, and code blocks.
- Use raw HTML only when Markdown cannot express the structure, such as `details` blocks or special wrappers.
- Add a `class` only when SCSS or JavaScript needs a hook.
- Check `assets/css/style.scss` before inventing a new class name.
- Prefer `{% raw %}{% comment %}{% endraw %}` blocks for explanations inside Liquid templates.
- Use `relative_url` on internal links printed by templates.
- When a page-level setting should control templates, put it in front matter or `_config.yml`.
- When many pages need shared ordered data, use `_data/*.yml`.
